## Description
After the module split (SPEC-011) and the headless core (SPEC-012), the game gets the foundations a real product needs:
- **Fully offline:** three.js and every other runtime file ship with the game; nothing loads from the internet.
- **Saves a child can't lose:** one versioned save, validated on load, a backup copy, automatic recovery from a broken save, persistent storage requested, and an export/import code for parents (moving to a new phone).
- **Friendly errors:** if something breaks, a calm "Oops" card with Continue / Restart level instead of a frozen screen; the last errors kept locally (never sent anywhere) so Andrei can read them on the device.
- **Code checks:** ESLint + Prettier and type checking from JSDoc (`tsc --checkJs`, no TypeScript build), run in CI on every push.
- **Versions:** a game version shown in the "How to play" / about page, `CHANGELOG.md`, git tags for releases, and the service worker version derived from it.
- **App lifecycle:** pause when the app goes to the background, resume cleanly; no memory growth over long sessions.

## Goal
- The game runs with the network off from the very first launch after install (PWA) — the base for Capacitor packaging later.
- No path in which a child loses progress without a way back.
- Every push is linted and type-checked; a release is a tag with a changelog entry.

### Saves
3. [2] One save module owns all storage: a single key `bebebe-save` with `{ version, progress, outfits, names, lang, seen, ... }`; old keys migrate into it once (old keys kept for one version as a fallback, then removed); a schema check on load (types and ranges; unknown fields dropped, missing ones defaulted).
   (from review RR-17, changed — the original plan loses data on a rollback, a stale tab or a key-presence rule) `bebebe-save` = `{ version, progress, outfits, names, lang, … }` (`seen` stays inside `progress`). The migration is an ordered pipeline: (1) read every old key raw; (2) compute the key-presence facts first (first launch for the language, `hadOwned` → `adoptWorn` only for saves without `owned`, flat fields, outfits `v` < 2 with `big: 0` → dad); (3) build `bebebe-save`, write it, read it back and validate it; (4) only then mark it migrated, storing a **fingerprint (hash) of each old key's raw value** in the migration record (fix round). **Old keys are never deleted or rewritten in this spec** (their removal is a later spec; the only exception is the grown-ups' "Erase all data on this device", AC 6b); `bebebe-skins` (v1-2d) is ignored. If an old key's fingerprint no longer matches (an old tab or an old cached build wrote it after the migration), it is merged again: best stars per level, the higher `unlocked`, union of owned items and seen scenes; coins and stock come from `bebebe-save`, not the larger of the two (Claude's choice); then the new fingerprint is stored. **Unknown fields and unknown worlds are kept unchanged and written back**; known fields are validated and defaulted.
   (fix round, architect review) **Schema rule: fields are only ever added; a change of a field's shape gets a new field name** (hard rule 7 gets this sentence). A save whose `version` is higher than the game's is played and written back with its own `version` and every field it had (never downgraded); in such a save a **known field that fails this version's validation is written back unchanged** — the default is used only in memory.
