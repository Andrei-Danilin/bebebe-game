# SPEC-012 — Headless core: game instances, input slots, events

Status: ready
Complexity: L
Branch: SPEC-012-headless-core
Decided by: Andrei (2026-11-22): the server computes the game (server-authoritative), many rooms on one server, up to 5 human Little Ones per game and a mode where a human plays the Big One. Everything below (API shape, slots, event list, what moves to the client): Claude (spec author).

## Description
Still nothing changes for the player. The core learns three things the server needs: (1) to hold **many games side by side**, each with its own state; (2) to take each player's controls from an **input slot** instead of reading the keyboard; (3) to **report what happened as events** (a push, a hug, a sound, a pop text, the result) instead of playing sounds, spawning particles or writing saves itself. The browser game becomes "core + a client that feeds inputs and draws events", exactly what an online client will be.

## Goal
- `src/core/` runs whole games in plain Node (`node --test`), many at once, deterministically.
- The core has no DOM/audio/storage access (`CORE_DOM_ALLOW` from SPEC-011 is empty).
- Up to 5 human Little Ones and an optional human Big One are possible in the core (the local UI still offers 1–2 players).

## Acceptance criteria
### Game instances
1. All mutable game state lives in one object made by `createGame(opts)` (`src/core/game.js`); the core works on the **active game** set by `useGame(g)` (one assignment, cheap; the server calls it before stepping a room — Node is single-threaded). `step(g, dt)` = `useGame(g); update(dt)` ~~with the existing fixed logic~~ (from review RR-08: there is no fixed step in live play today; see AC 1e). No other module-level mutable state remains in `src/core/` except `levelCache` and constants (a test lists the module-level `let`s of `src/core/` and allows only these). → `tests/core/instances.test.mjs` "two games stepped interleaved equal the same games stepped alone"
1b. (from review RR-07) Game entities hold only plain data: 3D models live in a client map keyed by entity id (`Map`/`WeakMap`), never on `littles[i]`/`big`; `structuredClone(g)` of a game after 60 s of play succeeds. The state test also rejects module-level mutable `const` containers in `src/core/` (typed arrays, `Map`, `Set`, arrays, objects that are not frozen tables) other than `levelCache`: the grids, the ledger, the autopilot memory, the hint timers and `pushWaves` move into the game object. → `tests/core/instances.test.mjs` "a game is plain data", `tests/modules.spec.js` "no mutable module-level containers in core"
1c. (from review RR-05) The core never reads or writes the client screen (`mode`). The game has `g.phase` (`"play" | "kindWalk" | "won"`), set only by the core; `canUseKit`, `throwKiss`, the autopilot and `simRun` read `g.phase`; the client sets its screen from the `result` event, and pause means "the client does not step the game". → `tests/modules.spec.js` "no `mode` identifier in src/core/", existing win/pause tests
1d. (from review RR-06) Menus and the Character screen draw a client-owned **showcase** game made with `createGame` and never stepped by the logic. Changing an outfit, a glove or the language re-dresses models and never calls `buildGame`/`resetWorld` or draws game `rng()`; only `startGame`, `selectWorld` and the end of a practice game build a playable game. The menu rotation of the Big One becomes a client view angle. → `tests/wardrobe.spec.js` "wardrobe changes draw no game rng" (`rngDraws` unchanged after 10 changes), existing wardrobe tests
1e. (from review RR-08) Step modes are documented and tested, live feel unchanged: `step(g, dt)` takes the `dt` the caller passes. Sim mode, `npm run balance`, `npm run test:core`, the bench and the future server use fixed steps of `CFG.BALANCE.SIM_DT`; the live client keeps one step per display frame with today's clamp. `docs/architecture.md` says so and says the balance report measures the fixed step, not the live loop. Determinism is tested at the fixed step (AC 7). A fixed live step (accumulator) is **not** part of this spec (decision D-11).
2. `createGame({ world, n, seed, mode: "local" | "online-a" | "online-b", slots })` where `slots` = up to 5 Little One slots `{ slot: "p1".."p5" | "bot1".."bot4", kind: "player" | "bot", look, name, glove, gloveCharges, kisses, kits, upgrades }` and the Big One slot `{ slot: "big", kind: "bot" | "player", skin, name }`. Missing Little One slots are filled with bots up to 5. → `tests/core/instances.test.mjs` "slots fill with bots"
   (from review, corrected) Today the glove is `progress.equip[pi]` and its charges come from the shared `progress.inv`; kisses and kits are one pool for local p1/p2. So a slot carries `glove` and the game gets a `stock` option `{ shared: true, kisses, kits, gloves: { mittens, mega } }` for local play (per-slot stock stays possible for online). The Big One slot also carries `boss` (`bossFor(world, n)`), and `opts` carries `practice` (AC 10). A game created with `seed` draws nothing from the rng before `createGame` returns except what today's `resetWorld` draws, in the same order.

### Inputs
3. The core reads controls only from `g.inputs[slot] = { mx, my, kiss, kit, act }` (vector clamped to length 1; buttons are edge flags consumed by the step). `inputFor` (keyboard, pads, sticks) moves to `src/client/input.js` and fills `p1`/`p2`; the kiss and kit buttons set flags instead of calling core functions. Local play is unchanged (1–2 players, one player on a phone). → existing `gameplay`/`phone` tests + `tests/core/inputs.test.mjs` "a player slot walks and throws a kiss from inputs only"
   (from review RR-13) Kiss/kit flags are consumed at the **start** of the step in slot order (where `autoThink` acts today), so the SPEC-011 baseline stays identical.
4. `big` slot `kind: "player"`: the core moves the Big One from `g.inputs.big` and skips his AI (turning, pushing and the button rules come in SPEC-015; here a test only checks he walks from inputs and the AI does not run). → `tests/core/inputs.test.mjs` "a player Big One is not driven by AI"

### Events
5. The core never plays sounds, makes particles, shakes the camera or writes pop texts: it appends events to `g.events` (the SPEC-008 log, extended): gameplay events as in SPEC-008 plus `sfx(name)`, `burst(kind, x, y, n, color)`, `pop(key, args, x, y)` (an `I18N` key and its arguments, so every client translates into its own language), `shake(t)`, `banner(world, n, type)`. The client drains `g.events` every frame and turns them into `SFX`, particles, pop texts and shake exactly as today. Purely visual randomness (particles, snow) is client-side. `CORE_DOM_ALLOW` is empty. → `tests/modules.spec.js` "core does not depend on the client" (empty allow-list), `tests/gameplay.spec.js` existing sound/pop-text tests
   (from review RR-11, changed) The event list also has: `pop(key, args, x, y, color, meaning)` (`meaning` picks the `POP_ART` sprite), `wave(x, y, r)` (wide push rings), `hint(kind, slot)` (first push of a player → kit hint; first `heard` → heard hint; practice hint steps), `mood(level)` when the Big One's anger changes; `banner(world, n, type)` carries no text (also the world-opened banner). The kit/heard/practice hint timers, the banner clock, pop-text lifetimes and the shake decay live in the client. The hooks `sfx`, `burst`, `pop`, `shake`, `banner`, `save` and `inputFor` of SPEC-011 AC 3b are removed (the test's hook list shrinks to what the client still needs, e.g. `rebuild`; each remaining hook has a comment why). → `tests/modules.spec.js` "no `L()` / `I18N` use in src/core/" and "core hook list"
6. **Result instead of saving:** the core never touches `progress`. On a win it emits `result { world, n, time, win, nobodyOut, fast, perSlot: { [slot]: { hugs, pushes, starCoins, kissesUsed, kitsUsed, gloveChargesUsed, rests } } }`; spending a kiss or a kit emits `spent(slot, kind)`. `src/client/progress.js` applies them (the ledger from SPEC-009, the shared local pool for two local players, saving a spent kiss at once as today). The win screen is unchanged. → `tests/gameplay.spec.js` existing reward tests, `tests/core/result.test.mjs` "result sums match the event log"
   (from review RR-12, corrected) `perSlot` uses today's stats (`hugs`, `playerHugs`, `rests`, `starCoins`, plus the counts the client needs); the reward itself is computed by `computeReward(progress, result)` in `src/core/progress-rules.js` (pure; used by the client and by Node tests), so the reward rules stay checkable without a browser.
6b. (from review RR-12) Mid-level economy changes keep today's timing: the core emits `coins(slot, "star", amount)` at star pickup and `spent(slot, "kiss" | "kit" | "glove")` when a kiss, a kit or a glove charge is used; the client applies and saves each at once (as today), so quitting or killing the app mid-level keeps them; `result` carries only the win lines. In a practice game the core emits no `coins`/`spent`/economy `result` (its own stock lives in the game, AC 10). The local kiss/kit pool stays one pool for p1/p2. The ledger lines of a level equal today's. → `tests/economy.spec.js` existing tests + "quitting mid-level keeps star coins and spent charges", `tests/core/result.test.mjs`

   (from review RR-13) Any re-recording of the baseline needs a commit message that says which gameplay events moved and why; flags consumed at the start of the step (AC 3) should make it unnecessary.
9b. (from review RR-14) `__bb.giveReward`, `__bb.throwKiss`, `__bb.useRescueKit` (and any other `__bb` function that bypasses events or inputs) are documented in `architecture.md` as thin shims. ### Test hygiene (from review)
11. (from review RR-71) Every test game is seeded before it is created: `resetGame` (`tests/helpers.js`) seeds the rng from a stable hash of the test title (not `Math.random`) and the failure message prints that seed; a smoke check fails on a test that calls `startGame(`/`resetWorld(`/`createGame(` without seeding first (`tests/tutorial.spec.js:356`, `:546` fixed); claims about a spread of outcomes (the bosses "bot goes to help" check, `tests/bosses.spec.js:141`) run over 10 seeds and assert a bound with margin instead of one seed. → `tests/smoke.spec.js` "every test seeds before it starts a game", `tests/bosses.spec.js` (changed)
