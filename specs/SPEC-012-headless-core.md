# SPEC-012 — Headless core: game instances, input slots, events

Status: ready
Complexity: L
Branch: SPEC-012-headless-core
Decided by: Andrei (2026-11-22): the server computes the game (server-authoritative), many rooms on one server, up to 5 human Little Ones per game and a mode where a human plays the Big One. Everything below (API shape, slots, event list, what moves to the client): Claude (spec author).

## Description
Still nothing changes for the player. The core learns three things the server needs: (1) to hold **many games side by side**, each with its own state; (2) to take each player's controls from an **input slot** instead of reading the keyboard; (3) to **report what happened as events** (a push, a hug, a sound, a pop text, the result) instead of playing sounds, spawning particles or writing saves itself. The browser game becomes "core + a client that feeds inputs and draws events", exactly what an online client will be.

## Goal
- `src/core/` runs whole games in plain Node (`node --test`), many at once, deterministically.
- The core has no DOM/audio/storage access (`CORE_DOM_ALLOW` from SPEC-011 is empty).
- Up to 5 human Little Ones and an optional human Big One are possible in the core (the local UI still offers 1–2 players).

## Acceptance criteria
### Game instances
1. All mutable game state lives in one object made by `createGame(opts)` (`src/core/game.js`); the core works on the **active game** set by `useGame(g)` (one assignment, cheap; the server calls it before stepping a room — Node is single-threaded). `step(g, dt)` = `useGame(g); update(dt)` ~~with the existing fixed logic~~ (from review RR-08: there is no fixed step in live play today; see AC 1e). No other module-level mutable state remains in `src/core/` except `levelCache` and constants (a test lists the module-level `let`s of `src/core/` and allows only these). → `tests/core/instances.test.mjs` "two games stepped interleaved equal the same games stepped alone"
   (fix round, architect review) The allowed module-level state is exactly: the active-game pointer, the hooks (`hooks.js`), `strictRng` / `rngOff` (test switches), `levelCache`, and the session economy data of `economy.js` (`progress`, `ledger`; AC 1b). The rng state and `rngDraws` live in the game object (each game draws its own sequence). `withGame(g, fn)` runs `fn` on `g` and restores the previously active game (also when `fn` throws), for code that touches a second game (the showcase, AC 1d).
1b. (from review RR-07) Game entities hold only plain data: 3D models live in a client map keyed by entity id (`Map`/`WeakMap`), never on `littles[i]`/`big`; `structuredClone(g)` of a game after 60 s of play succeeds. The state test also rejects module-level mutable `const` containers in `src/core/` (typed arrays, `Map`, `Set`, arrays, objects that are not frozen tables) other than `levelCache` and, in `economy.js`, `ledger` (fix round: the session coin book stays outside the game — it survives `startGame` and the shop writes it): the grids, the autopilot memory, the hint timers and `pushWaves` move into the game object. → `tests/core/instances.test.mjs` "a game is plain data", `tests/modules.spec.js` "no mutable module-level containers in core"
1c. (from review RR-05) The core never reads or writes the client screen (`mode`). The game has `g.phase` (`"play" | "hugEnd" | "kindWalk" | "won"`; fix round: `hugEnd` = the last hug's animation, `CFG.HUG_ANIM`, before the kind walk), set only by the core; `canUseKit`, `throwKiss`, the autopilot and `simRun` read `g.phase`; the client sets its screen from the `result` event, and pause means "the client does not step the game". → `tests/modules.spec.js` "no `mode` identifier in src/core/", existing win/pause tests
1d. (from review RR-06) Menus and the Character screen draw a client-owned **showcase** game made with `createGame` and never stepped by the logic. Changing an outfit, a glove or the language re-dresses models and never calls `buildGame`/`resetWorld` or draws game `rng()`; only `startGame`, `selectWorld` and the end of a practice game build a playable game. The menu rotation of the Big One becomes a client view angle. → `tests/wardrobe.spec.js` "wardrobe changes draw no game rng" (`rngDraws` of the play game unchanged after 10 changes), existing wardrobe tests
1e. (from review RR-08) Step modes are documented and tested, live feel unchanged: `step(g, dt)` takes the `dt` the caller passes. Sim mode, `npm run balance`, `npm run test:core` and the future server use fixed steps of `CFG.BALANCE.SIM_DT`; the live client keeps one step per display frame with today's clamp. `docs/architecture.md` says so and says the balance report measures the fixed step, not the live loop. Determinism is tested at the fixed step (AC 7). A fixed live step (accumulator) is **not** part of this spec (decision D-11).
1f. (from review RR-16; fix round: moved here from SPEC-011 AC 7b) Drawing functions change no menu or game state: the resets that `drawUI` does today — `shopTab`, `wardrobePage`, `toast`, `mapBgCache`, closing the name input — happen in the screen-change functions of `src/client/flow.js`, and the banner's start time is set there too. → `tests/menus.spec.js` "a screen change in sim mode leaves the same state as in a rendered page": for the transitions home → Character, Character → map, map → home, win → shop, shop → map, the fields `mode`, `shopTab`, `wardrobePage`, `toast`, `mapBgCache` (cleared or not) and "name input open" are equal in a sim page and a rendered page.

### Events
5. The core never plays sounds, makes particles, shakes the camera or writes pop texts: it appends events to `g.events` (the SPEC-008 log, extended): gameplay events as in SPEC-008 plus `sfx(name)`, `burst(kind, x, y, n, color)`, `pop(key, args, x, y)` (an `I18N` key and its arguments, so every client translates into its own language), `shake(t)`, `banner(world, n, type)`. The client drains `g.events` every frame and turns them into `SFX`, particles, pop texts and shake exactly as today. Purely visual randomness (particles, snow) is client-side. `CORE_DOM_ALLOW` is empty. → `tests/modules.spec.js` "core does not depend on the client" (empty allow-list), `tests/gameplay.spec.js` existing sound/pop-text tests
   (from review RR-11, changed) The event list also has: `pop(key, args, x, y, color, meaning)` (`meaning` picks the `POP_ART` sprite), `wave(x, y, r)` (wide push rings), `hint(kind, slot)` (first push of a player → kit hint; first `heard` → heard hint; practice hint steps), `mood(level)` when the Big One's anger changes; `banner(world, n, type)` carries no text (also the world-opened banner). The kit/heard/practice hint timers, the banner clock, pop-text lifetimes and the shake decay live in the client. The hooks `sfx`, `burst`, `pop`, `shake`, `banner`, `save`, `inputFor`, `keys`, `sticks`, `pads` of SPEC-011 AC 3b are removed (the test's hook list shrinks to what the client still needs, e.g. `rebuild`; each remaining hook has a comment why). (check of the SPEC-024 fix round) With `save` removed, `economy.js` stays plain data and the client saves after every `economy.js` change it applies (events of AC 6/6b, shop spends, `addCoins`). → `tests/modules.spec.js` "no `L()` / `I18N` use in src/core/" and "core hook list"
   (fix round, code review) Effect events (`sfx`, `burst`, `pop`, `shake`, `wave`, `hint`, `mood`, `banner`) go into a **separate drain queue** `g.fx`, which the client empties every frame (sim and Node drain it every step, or create the game with `fx: false` so nothing is queued); it is not capped and never pushes gameplay events out. Gameplay events stay in `g.events`, capped at the existing `CFG.EVENT_LOG_MAX` (5,000); the baseline and determinism comparisons run with a cap large enough for the whole run, so nothing is cut.
6. **Result instead of saving:** the core never touches `progress`. On a win it emits `result { world, n, time, win, nobodyOut, fast, perSlot: { [slot]: { hugs, pushes, starCoins, kissesUsed, kitsUsed, gloveChargesUsed, rests } } }`; spending a kiss or a kit emits `spent(slot, kind)`. `src/client/progress.js` applies them (the ledger from SPEC-009, the shared local pool for two local players, saving a spent kiss at once as today). The win screen is unchanged. → `tests/gameplay.spec.js` existing reward tests, `tests/core/result.test.mjs` "result sums match the event log"
   (from review RR-12, corrected; fix round) `perSlot` uses today's stats (`hugs`, `playerHugs`, `rests`, `starCoins`, plus the counts the client needs); the perSlot counts are **for display only and never go into the ledger** (the coins come from the reward lines and the immediate events of AC 6b, so nothing is counted twice). The reward itself is computed by `computeReward(progress, result)` in `src/core/progress-rules.js` (pure; used by the client and by Node tests). The game's core code no longer writes `progress` or `ledger` during a level: it emits events, and the client applies them through `economy.js` and saves.
6b. (from review RR-12) Mid-level economy changes keep today's timing: the core emits `coins(slot, "star", amount)` at star pickup and `spent(slot, "kiss" | "kit" | "glove")` when a kiss, a kit or a glove charge is used; the client applies and saves each at once (as today), so quitting or killing the app mid-level keeps them; `result` carries only the win lines. In a practice game the core emits no `coins`/`spent`/economy `result` (its own stock lives in the game, AC 10). The local kiss/kit pool stays one pool for p1/p2. The ledger lines of a level equal today's. → `tests/economy.spec.js` existing tests + "quitting mid-level keeps star coins and spent charges", `tests/core/result.test.mjs`
