# Architecture — bebebe-game v2 (3D)

The shell `index.html` + the ES modules in `src/` (+ PWA files, see below), served over http only (SPEC-011: `npm run serve`, Pages, the installed app). The shell has a small non-module script (`window.__bbBoot`: the first error handlers, the WebGL2 probe, the start-failure texts in four languages, the `file://` notice; see Errors and lifecycle), one `<script type="importmap">` and the entry script `<script type="module" src="./src/client/main.js?v=<hash>">` — no game code (SPEC-011 AC 1, `tests/modules.spec.js` "index.html has no inline game code"). An entry script's `src` is not remapped by the import map, so `npm run precache` writes `main.js`'s version into the tag itself. The import map resolves the bare name `"three"` to the vendored build `./vendor/three/three.module.js` (SPEC-025 AC 1; it imports `./three.core.js`, also mapped) and pins every `./src/…` and `./vendor/three/…` file to `?v=<hash>` (`npm run precache`, see PWA). No file is loaded from another host: the game runs offline from the first launch (`tests/offline.spec.js`). Two stacked canvases inside `#wrap`: `#gl` (WebGL, Three.js) below, `#game` (2D, UI and input) on top.

## Layers (keep them apart)
1. **Logic** (`src/core/`, see Modules) — world, level generator (pure: no Three.js, no theme; the world only picks the seed), pathfinding, rules, bots, the Big One, items, progress. Works in "logic pixels": 960×640, `CELL = 32` (1 cell = 1 unit in 3D). Knows nothing about Three.js.
2. **3D** — builds meshes from the world (`buildMap3D`, `buildCharacters`) and copies state into them every frame (`syncScene` → `syncLittle`, `syncBig`, `syncItems`, `syncStars`, `syncKisses`, `updateCone`). Only reads game state.
3. **2D UI** — menu screens (home, level map + level card, story, Character — the old shop: Progress, Items, Wardrobe and Upgrades tabs; SPEC-017, SPEC-026), HUD, name tags, timers, mini-map; positions of world things via `toScreen(x, y, heightPx)`. Buttons are registered each frame in `ui.buttons` (`src/client/state.js`) and hit-tested on `pointerdown` (on the map and the story chapters: on `pointerup`, see Screens and menus). SPEC-025 AC 7d: the list has a generation — `ui.screenSeq` goes up on every screen change (`screenChanged()` of `state.js`: `setMode`, a shop tab, a wardrobe page, a story page or chapter, a scene page, the world, an armed reset / buy), `drawUI` stamps `ui.buttonsGen` when it draws the list; a tap on an older list runs nothing (`input.js`), so two taps in one frame never act twice. Draws in **UI space** `UW × UH` (see Phone mode), never in world `W × H`.

## Modules (SPEC-011)

The game is ES modules served over http. `src/core/` is the game itself and runs in Node too (`node -e "import('./src/core/index.js')"`). `src/client/` is everything a player sees, hears and touches; `src/client/main.js` starts it (see "The client" below).
- **Dependency rule** (AC 3, `tests/modules.spec.js` "core does not depend on the client"): `src/core/` imports only `src/core/**`, `src/i18n.js` and `src/story.js`; never three.js or `src/client/`; never `document`, `window`/`globalThis`, `localStorage`, `navigator`, `requestAnimationFrame`, `Audio`/`AudioContext`. Exceptions would go into `CORE_DOM_ALLOW` in that test — it is empty. The core, `src/i18n.js`, `src/story.js`, `src/client/look.js` and `src/client/art-names.js` hold only declarations at top level (no storage, DOM or `window.__bbStrictRng` read at import; the client calls `setStrictRng(window.__bbStrictRng === true)` and seeds from `window.__bbSeed`).
- **Hooks** (AC 3b; SPEC-012): the core reaches the client through `hooks` of `src/core/hooks.js`, registered once with `setHooks({ … })` before `await loadSave()`; unset ones are no-ops (Node). Since SPEC-012 one hook is left: **`rebuild`** (the 3D scene must be rebuilt at once, inside `buildGame`, for the game just built). It runs under `noGameRng`; a new hook name throws in `setHooks`. Everything else the core tells the client is an event (see "Headless core" below): effects in `G.fx`, the economy, the win and the practice win in `G.events`; controls come in through the input slots `G.inputs`.
- **Live bindings rule** (AC 5): a module-level `let` is reassigned only in its own module; others call its setter (column 4 below; ESLint `no-import-assign`). Client state that several modules write is the one `ui` object of `src/client/state.js` instead of many setters. `__bb.mode = x` and the other `__bb` setters call them.
- **Economy** (AC 2b; SPEC-012 AC 6): `economy.js` holds the session's `progress` and coin book `ledger` as plain data: `addCoins` / `spendCoins` change them, it never touches storage and never saves. The game never writes them during a level: the client applies the game's `coins` / `spent` / `result` events (`flow.js` `applyGameEvent`) and saves after every change it makes (`saveProgress`, `progress.js`: queues the whole save in `save.js`). The client loads the save and hands it over with `setProgress`.
- **Saves at start** (SPEC-025 AC 3b; replaces SPEC-011's `initSaves`): nothing reads storage at import. `boot()` is async and runs **`await loadSave()`** (`save.js`) once, after `setHooks`, before `initInput` and the first `resetWorld`: the storage probe → read every save key and old key → no `bebebe-save`: migrate the old keys; a valid one: use it, merge stale old keys, rotate the session copy; a broken one: recover from a copy → apply it (progress through the core's `loadProgress`, outfits, names, language, `adoptWorn` only on a real migration, else `fitOutfitsToOwned`) → `G.world = progress.lastWorld`, `G.level = unlocked` → when something changed: write, read back → `persist()`. `tests/modules.spec.js` reloads every fixture of `tests/fixtures/saves/` (old keys) against `tests/fixtures/saves-loaded.json`; `tests/saves.spec.js` covers the rest (see Save data).
- **`CFG` and `LOOK`** (AC 2c): rules, generator and balance numbers are `CFG` in `src/core/config.js`; the look/UI numbers (`CAM_*`, `PHONE_*`, `MINIMAP_*`, `ART`, `PAPER*`, `*_LOOK`, `BANNER_*`, `PAD_*`, …) are `LOOK` in `src/client/look.js`, same key names. Two `*_LOOK` keys stay in `CFG` (`CONFIG_LOOK_ALLOW` in the test): `TUTORIAL_LOOK` (the practice game reads `dadStart`) and `HEAR_LOOK` (a hearing rule). SPEC-032 added the `LOOK` groups `TIPTOE_BTN` (the 👣 button), `LANG_SCREEN` (the language screen) and `BUBBLE_MIN` (the comic bubbles' smallest text). `__bb.CFG` is a `Proxy` (`CFG_ALL`) over both: reads, writes, `delete` and key lists reach the object that holds the key, so tests change and restore any key through it.
- **Same game** (AC 7): the moved code must play exactly the references recorded on the one-file game — `tests/fixtures/events-baseline.json` (event logs, rng draws, actor snapshots of fixed runs with `baseline-stocked.json`) and `saves-loaded.json`. `BB_RECORD_REFERENCE=1` refuses to write them once `src/core/` exists: a reference is never re-recorded to make moved code pass.

## Headless core (SPEC-012)

The core runs whole games without a client: in the browser, in Node (`npm run test:core`) and, later, many rooms on one server (SPEC-013).
- **Game object** (AC 1): all mutable state of one game is one plain-data object — `newGame(opts)` makes it, `createGame(opts)` builds it (`buildGame` on it) and returns it without making it active. Its fields: world, level, players, `phase`, the entities (`littles`, `big`, `items`, `bonusStars`, `kisses`), timers and ids, `stats`, `events`, `fx`, `inputs`, `stock`, the map (`obstacles` … `spawns`, the typed-array grids, `levelInfo`), the practice state (`practice`, `tutorialGame`, `tut`, `tutorialInv`), the autopilot (`autoOn`, `autoStyle`, `autoNavs`, `autoMove`) and its rng stream `rng = { s, draws }` (mulberry32's state). `structuredClone(g)` copies a whole game that plays on exactly like the original (`tests/core/instances.test.mjs`).
- **The active game** (`src/core/active.js`): the core works on `G`; `useGame(g)` sets it (one assignment), `withGame(g, fn)` runs `fn` on `g` and restores the previous game (also on a throw), `step(g, dt)` = `useGame(g); update(dt)`. Every core and client read goes through `G.<field>`. Allowed module-level state in `src/core/` is exactly: `G`, the hooks, `rngOff` / `strictRng` (test switches), `levelCache` (pure per level key, shared) and `economy.js`'s `progress` / `ledger` (session data), plus constant tables — `tests/modules.spec.js` "no mutable module-level containers in core" lists them.
- **Phase vs screen** (AC 1c): the game has `G.phase` (`"play"` → the last hug `"hugEnd"` → the walk home `"kindWalk"` → `"won"`), set only by the core; the core never names `mode`. The screen (`mode`, `setMode`) and the last reward are the client's (`flow.js`). Pause = the client does not step the game; the 💋 / 🩹 keys and buttons work only on the play screen, and a press still waiting when the screen leaves play is dropped (`setMode`).
- **Slots** (AC 2): `createGame({ world, n, seed | rng, mode: "local" | "online-a" | "online-b", slots, stock, practice, fx })`. Little One slots `{ slot: "p1".."p5" | "bot1".."bot4", kind: "player" | "bot", look, name, glove, gloveCharges, kisses, kits, upgrades }` in their order (at most `teamSize()`: 5, a practice game player + bot), missing ones are bots (`fillSlots`); the Big One's slot `{ slot: "big", kind: "bot" | "player", skin, name, boss }` (`boss` defaults to `bossFor`). The stock `{ shared, kisses, kits, gloves: { mittens, mega } }` is what kisses, kits and glove charges are spent from (local play: one pool for p1/p2, kept equal to the saves by the client's `syncStock` before every step and frame; per-slot fields exist for online play). The slots draw the same rng calls in the same order as before (players, then bots).
- **Input slots** (AC 3, 4): the core reads controls only from `G.inputs[slot] = { mx, my, kiss, kit, act, tiptoe }` of player slots — the stick clamped to length 1 (`tiptoe` cuts it to `TIPTOE_MULT`), the buttons edge flags fired and consumed at the start of the step in slot order (`readInputs`, where the autopilot decides too). The client's `fillInputs` writes the device sticks (keys with its own key map, pads, touch sticks) into p1/p2 before each step; keys, pad buttons and HUD buttons set the flags (`pressKiss` / `pressKit`). A Big One slot of kind `"player"` walks from `G.inputs.big` (`updateBigPlayer`) and his AI does not run (the rules for a player Big One: SPEC-015).
- **Events** (AC 5, 6, 10): see "Sim mode and the event log" for the list. Gameplay events stay in the capped `G.events`; effects go into the uncapped `G.fx` (`emit`), which the client drains every step (`fx.js` `drainEvents`: sounds, particles, pop texts translated with `L()`, shake, the wide-push rings, the hint timers); the purely visual randomness (particles, the hug hearts, snow) is the client's `vrand`. A Node or server game is made with `fx: false` (nothing queued — that also drops the `{ type: "game" }` hand-off, so such a game reads `coins` / `spent` / `result` / `practiceWin` from `g.events` itself) or drains `g.fx` itself.
- **Result and economy** (AC 6, 6b): the game spends from its stock and logs `spent`, logs star `coins`, and on a win `result` (`levelResult`). The reward is the pure `computeReward(progress, result)` (`progress-rules.js`): `{ reward, lines, world }`. The client applies the events after the step (`applyGameEvent`): star coins and spent charges into `progress` and saved at once (quitting mid-level keeps them, as before), the result through `payLevel` (world stars / won / unlocked, then each coin line through `addCoins` and a save — the same ledger lines as before), then the win screen. Order note: when the win comes from the walk home ending early (at the start of a step), the reward's coins lines are logged after that step's other events (they used to come right after `win`); the ledger lines and amounts are the same. `perSlot` counts are for display only. A practice game spends from its own stock and logs no `coins` / `spent` / `result`.
- **Practice games** (AC 10): `createGame({ practice: step | { step, map, hearts, bots, stock, script } })` → `G.practice` (plain data; `script` is an id — `"game1"`, the scripted push of practice 1 in `practice.js`). A practice win logs `practiceWin`; the client's tutorial goes on after the step (`tutorialNext`), no hook re-enters the core. The client keeps the step of the next local game in `tutorial.js` `practiceStep`.
- **The client's games** (AC 1d): every build is a new game object made active (`flow.js`): `playWorld` (startGame, selectWorld, the end of a practice game) continues the **local rng stream** `localRng` (`seedRandom`, `window.__bbSeed`), `resetWorld` builds the menus' **showcase** from a copy of that stream's state (it never draws it). The session's carry-over (the event log until the next level starts, ids, reward due, the autopilot switches) is passed with `createGame({ keep })`. Wardrobe, glove and try-on changes re-dress the shown game (`redress`), never rebuild it; the Big One's turn in the menus is the client's view angle `ui.menuSpin`. The 3D models live in the client's map `models` (`three/characters.js`, `modelOf`), keyed by entity — never on the entities. Drawing changes no state (AC 1f): the menus' resets happen in `setMode`.
- **The live loop** (SPEC-034, D-11): `main.js` `frame` → `tick` → in play (and not on a portrait phone) `runFrame(real)` of `fx.js` → `frameSteps(acc, frameTime)` of `core/util.js`. The accumulator `ui.acc` takes the real frame time clamped to `CFG.MAX_FRAME` (0.25 s: a tab coming back does not fast-forward), gives `n = floor(acc / CFG.STEP)` whole steps of exactly `CFG.STEP` (1/60 s), at most `CFG.MAX_STEPS` (8) per frame (the excess is dropped), and keeps the remainder. The devices are read once per frame (`fillInputs`) and apply to all `n` steps of it (a 💋 / 🩹 press fires at the first). A step that leaves play or builds another game (a win, a result, the next practice game) ends the frame's stepping. A new game (`flow.js`) starts the accumulator at `CFG.STEP_PHASE` × `CFG.STEP`: at 60 Hz the frame times sit on the step boundary and rAF jitter would give 0- and 2-step frames. Pause, menus, a portrait phone and the background feed nothing (`runFrame` does nothing outside `play`).
- **Game time vs frame time** (SPEC-034 AC 3): game time moves only in the whole `CFG.STEP` steps of the loop above; the core and the rules never see the frame time. Frame time (the real time of the frame, at most `LOOK.VIEW_DT_MAX` 0.05 s) ages only client-side things that are not game state: the camera (`updateCamera`, shake), the mini-map fade, `ui.T` (the animation clock of drawing), flying texts, particles and wide-push rings (`viewTick`), the menu spin, and the map's toast and world banner (`mapTick`). The level banner and the Big One hint timers (`bannerTick`, `hintTick`) count game steps. Pause, menus and the background feed nothing to the accumulator. `__bb.frame(seconds)` feeds `runFrame` a simulated frame time (tests: the same level at 30 / 60 / 120 / 144 Hz gives the same game, `tests/fixedstep.spec.js`); `__bb.acc` is the accumulator (read-only, below `CFG.STEP` between frames); `__bb.update(dt)` is one step of the caller's `dt` (`stepGame`: devices, one core step, one view tick) that does not touch the accumulator.
- **Step modes** (AC 1e, SPEC-034): `step(g, dt)` takes the `dt` the caller passes, and every caller passes `CFG.STEP` (1/60 s): live play (through the accumulator above), sim mode, `simRun`, the autopilot, `npm run balance`, `npm run test:core`, `npm run bench:core` and the future server. So the same inputs give the same game on any screen and the balance report measures the game players get. Determinism is tested at the fixed step (`tests/core/run.test.mjs`, `tests/core/step.test.mjs`). The split reference test in `tests/modules.spec.js` is the one exception: the references were recorded at 1/30 s, so it steps at its own `REF_DT` (`runLevel`'s `dt` argument) — it checks the code split, not the step size.
- **Speed** (AC 8, `npm run bench:core`, `scripts/bench-core.js`): 100 games side by side, 60 game-seconds at 60 steps/s = `CFG.STEP` (1 autopilot player + 4 bots each, a won room stops). On Andrei's laptop: ~3 ms to build a game (2026-11-25); ms per game step at 1/60 s (SPEC-034, 314081 steps): median 0.034, p95 0.124 (at 1/30 s in the same session: 0.028 / 0.137; target p95 ≤ 1 ms).
- **Core API** (`src/core/index.js`): re-exports every core module (`export *`); the server surface is `createGame`, `useGame`, `withGame`, `step`, `simRun`, `newInput`, `computeReward`, `levelResult`, `setProgress`, `CFG` and the tables. An explicit named API stays in BACKLOG.

## The client (SPEC-011 Phase C)

The client is the ES modules of `src/client/` (rows in the module table above); find code by module and symbol, never by line numbers.
- **Start** (`main.js`, the only client module with top-level statements — `tests/modules.spec.js` "only main.js starts the game"): every other module only declares; its start-up work is an `export function init…()` marked `// called once by main.js`. `main.js` runs one guarded `boot()` (SPEC-025 AC 7b: a throw → `failStart`) in the start order of the one-file game: `initErrors` → no WebGL2 (`hasWebGL2`) → `failStart("noWebGL")` and stop → `setStrictRng(window.__bbStrictRng === true)` and the `window.__bbSeed` seed → `initArt` (sprite slots) → `initScreen` (`sim` from the URL, `body.phone`, resize listeners) → `setHooks({ … })` → `await loadSave()` (`boot()` is async; a rejection → `failStart`) → `initInput` (keyboard and pointer listeners) → `initThree` (the WebGL renderer) → `fit()` → `initScene` (background, fog, lights, sun; `three/setup.js` imports no client module, so it is a leaf) → `initCamera` (`fitCamera`, the values that depend on it: `camDist`, `cam`, the shadow axes; the phone `onFit` through `setOnFit`) → `initMaterials` (gradient texture, `hatchSun`, the ground canvas) → `initSync` / `initCharacters` (view cone, hug zone and the groups added to the scene) → `initPreviews` → `initLifecycle` (SPEC-025: hide, blur, WebGL context loss) → `fit()`, `resetWorld(1)`, `artGate()` → `__bbReady` → the frame loop `frame` (asks for the next frame first, then runs `tick` in a guard: an error → `reportError`) → `registerServiceWorker()` → `installDebug()` (`window.__bb`, `debug.js`). Declarations evaluate when the modules load (before `main.js` runs); a value that depends on an earlier start step is a `let` its init function sets (`// set by init…()`). The client's imports form cycles, and inside a cycle a module can evaluate before a module it imports: no top-level declaration may read a binding of a module evaluated later in its cycle (`tests/modules.spec.js` "no top-level read of a module evaluated later in the same import cycle").
- **State**: per-frame drawn state and the UI state several modules write — `buttons`, `hudRects`, `texts`, `particles`, `shake`, `banner`, `shopTab`, `wardrobePage`, `storyPage`, `storyScene`, `toast`, `mapSwipe`, `openedWorld`, the `*Info` / `*Rect` objects the tests read, the counters `renders`/`draws`/`sounds`, the frame clock `T` — are properties of **`ui`** (`state.js`, a leaf module), written in place (`ui.shake = v`). Module state with one owner keeps its `let` and a setter for other modules: `setSkinSel`/`setSkinKeep` (`outfits.js`, written by `save.js`: `loadSave`, a restore, an import), `setNamesTyped` (`names.js`, written by `save.js`), `setOnFit` (`screen.js`, the phone camera registers it), `setCtx` (`screen.js`: `paintGround` draws the ground texture through the 2D helpers), `setHouseInfo` (`houses.js`, cleared by `buildMap3D`), `setTutorial` (`tutorial.js`, cleared by `resetMenus`).
- **Storage** (SPEC-025 phase 2): `storage.js` is the only code in `src/` that touches `localStorage` (`localBackend`), and `save.js` is the only module that calls a backend. The game's save calls — `progress.js` `saveProgress` (after every change of progress the client makes: the game's economy events, the shop, the wardrobe, the screens), `writeOutfits` (from `outfits.js`), `writeNames` (from `names.js`), `setLang` — each queue the whole save (`queueSave`); `errors.js` stores `bebebe-errors` through `save.js`. The stored save is read only by `loadSave()`, once at start (`tests/modules.spec.js` "only the storage backend touches localStorage; loadSave once at start"). See Save data.
- **`window.__bb`** (`debug.js`): built from explicit imports; a live value is a getter (and a setter that calls the owner's setter, or writes `ui`), never a copy; `tests/modules.spec.js` "the __bb surface is unchanged" checks the kinds. `CFG_ALL` (the `__bb.CFG` Proxy) and `SIM_DRAWN` live there too.
- **Module names that differ from spec AC 2 / 2e** (the spec lets the run adjust them): `state.js` (the `ui` object above), `names.js` (players' names: their own save key and helpers), `shop.js` (the Character screen's buy actions, used by several tabs), `fx.js` (the effect hooks `pop`/`burst`/`fx`/`banner`), `ui/menu.js` (frame and button helpers shared by every menu screen), `ui/screens.js` (`drawUI` and the per-mode dispatch `drawOverlay` / `drawOverlayPhone` — what AC 2 called `ui/overlay.js` / `overlay-phone.js`; the screens themselves are the AC 2e modules: Items in `ui/character/items.js`, pause / win / lose in `ui/win.js`), `ui/character/tabs.js` (the Character screen's tab bar, shared by its four tabs), `three/look3d.js` (`look3D()`, the tests' view of the 3D scene). There is no `three/skins.js`: the wardrobe previews are `three/previews.js` (AC 2e).
- **Where the old `index.html` blocks went**: КАРТИНКИ → `art.js` (+ the canvas helpers in `ui/draw.js`); ЭКРАН → `screen.js`; saves, wardrobe, names, worlds → `progress.js`, `outfits.js`, `names.js`, `shop.js`, `flow.js` (SPEC-025: the storage itself → `save.js` + `storage.js`); screens / map / story / scenes → `flow.js`, the tutorial machine → `tutorial.js`; ЗВУК → `sound.js`; УПРАВЛЕНИЕ → `input.js`; client effects → `fx.js`; 2D-СЛОЙ → `ui/**`; 3D → `three/**`; ГЛАВНЫЙ ЦИКЛ → `main.js`; `window.__bb` → `debug.js`.
## Worlds and level keys (SPEC-006, SPEC-016)
- **A level is `(world, n)`**: SPEC-016 world lists (all `Object.freeze`d): **`MAIN_WORLDS`** = `["park", "field", "city", "school"]`, **`BONUS_WORLDS`** = `["beach", "winter"]`, **`WORLDS`** = `[...MAIN_WORLDS, ...BONUS_WORLDS]` (story order = menu order; the world is also the level's place, `THEMES[world]`), `n` = 1…`levelsPerWorld()` = `CFG.WORLD_TYPES.length` (20). `levelPos(n)` = clamped `n − 1`. **`levelKey(world, n)`** = `"world:n"` keys `levelCache` and the fixtures.
- **Three ways to use a world** (SPEC-016) — never mix them:
  - **by name**: seeds (`WORLD_SEED`), `levelCache`/`levelKey`, `levelReport`, `levelInfo.world`, `progress.worlds[w]`, `progress.lastWorld`, `THEMES[w]`, `I18N.*.worlds[w]`, balance report rows, `CFG.BALANCE` entries;
  - **by difficulty index** **`worldDifficulty(world)`** = `CFG.WORLD_DIFFICULTY[world] ?? 0` (park 0, field 1, city 2, school 3, beach 3, winter 4): `levelBoost`, `bigHearts` (→ `difficulty()`), `rewardBase`, `fastTarget`;

## Level types and the generator (SPEC-002)
- **`generateLevel(world, lv, attempt)`** (pure, theme-free, seeded only by `mulberry32(levelSeed(world, lv) * 7919 + attempt * 104729 + 13)`): builds the layout context `lc` (`lv, attempt, type, tier, rng, ri, items, occ, reserve, isFree, hWall, vWall, place(n, make, w, h, m, ok)`, `small`, `bigPt`, `doors`, `homes`, `meta`) → **`placeHomes(lc, variant)`** (Little Ones' house 7×6 top-left with `safe`, beds and spawns; the Big One's 6×6 house through `bigHouse()` bottom-left `"side"` or bottom-right `"diagonal"`; `CFG.DOOR_APRON` cells reserved in front of every door; `variant` = `"side"` for classic, `CFG.LAYOUT[type].homes` if set, else the seed) → **`LAYOUTS[type](lc)`** → mirror `fx`/`fy` (not on level 1; mirrors items, danger `exits`, `meta.areas` and the doors) → flowers. Returns `{ type, items, small, big, flowers, doors: { small, big }, meta }`; `doors` = door openings `{ x, y, w, h, dx, dy }` (outward direction) for the fairness rules; `meta` = layout facts (`deadEndsBefore/After` for the maze, `areas` — plazas, bridges, rooms + doors, arena block/ring/gaps — for tests, `bad` = the layout could not be built, `vertical` for the river).
- **Layouts** (all sizes in `CFG.LAYOUT[type]`): `classicLayout` = the old body, byte-for-byte (fixture `tests/fixtures/level1.json`); `meadowLayout` (ponds, trees, rocks, bushes); `mazeLayout` (3-cell modules: Kruskal perfect maze, home areas and 5×5 plazas opened, braided to ≤ `CFG.MAZE_DEAD_ENDS`, walls as `maze` cells); `villageLayout` (`floor` `square` + fountain `pond`, `cottage` blocks with `street` margin, bushes next to cottages); `riverLayout` (`water` pieces between the houses, bends, `floor` `bridge` with `across: "x"|"y"`, bushes split between banks); `roomsLayout` (diagonal only: two wings with BSP rooms, `build` walls, `tile` floor, outside doors into both yards); `arenaLayout` (diagonal only: `arena` block and ring with gaps, optional half-ring). `emitWalls(items, occ, wall, kind)` turns a wall-cell grid into wall rectangles.
- **Item kinds and flags** (`applyWorld` → `obstacles`): `wall` kinds `home`/`bighome`/`build`/**`maze`**/**`arena`** (and `hedge` from the fallback) — move + sight; **`cottage`** — rect, move + sight; **`water`** — rect, move only (sight passes); `pond` — move only, `fountain: true` for the village fountain; `tree`/`rock` — circles, both. `floor` kinds `wood`/`tile`/**`bridge`** (`across` kept)/**`square`** are walkable ground only. Bridges are gaps between water pieces, so they are free cells.
- **`buildGrids()`** rasterizes: each obstacle marks only the fine/coarse cells of its own bounding box (same rules as `covers()`), because a level may be built up to `CFG.LEVEL_ATTEMPTS` times; then `moveGridBig`/`blockedBig` add the safe zone.
- **`validateLevel(gen, type)`** (on the applied world) → `{ ok, fails, seen, freeRatio, bigReachAll, smallReachAll, housePath, doorClear, deadEnds: { count, longest, before }, bushes }`. Rules: `smallReach` (`connectivity()`), `bigReach` (`floodCells` on `blockedBig` from his spawn), `housePath` (A* on `blockedBig`, √2 diagonal, shortest big-door → cell-in-front-of-small-door pair, in `CFG.HOUSE_PATH`; skipped for `classic`), `free` (`CFG.FREE_MIN[type]`, outside both houses), `doors` (`CFG.DOOR_APRON` rows in front of every door free on both grids), `deadEnds` (`deadEndScan`: 2×2 free windows of `blockedBig` as nodes, leaves peeled; maze: count outside houses and aprons ≤ `floor(before × MAZE_DEAD_ENDS)`, others: `longest ≤ CFG.DEAD_END_MAX`), `bushes` (`CFG.BUSH_MIN`), plus `layout:<meta.bad>`.
- **`buildLevel(world, lv)`**: attempts 0…`LEVEL_ATTEMPTS - 1`, first `ok` wins. Fallback: rebuild the attempt with the lowest `failScore` (fail count, +100 if a reach rule failed), fill with `hedge` every free cell the Little Ones can't reach or (outside their house) the Big One can't reach, `console.warn`. Sets `reachable`; returns the report without `seen`/`ok`, plus `tier`, `attempt`, `attempts`, `fallback`, `rejects`, `ms`.
- **`loadLevel(world, lv)`** (from `buildGame`, with `G.world, G.level`): `levelCache` (`levelKey(world, lv)` → accepted attempt) rebuilds that attempt directly and re-validates it; a cached attempt that no longer passes (e.g. `CFG` changed) is dropped and the level is built from attempt 0. Fallback results are not cached. Sets **`levelInfo`** `{ world, lv, type, attempt, fallback, cached, ms }`. `clearLevelCache()` empties the cache.
- **`levelReport(world, lv)`** (tests): saves the world (`keep` = `obstacles, bushes, floors, decor, trees, flowers, safeZone, dangerZone, spawns, reachable` + copies of the five grids), runs `buildLevel`, restores everything in `finally`. The comment above `applyWorld` says it: new world state → add it to `keep` and to `__bb.worldState`.
- **Bots on new layouts**: `fleePoint` only picks `reachable` cells and falls back to `freePointNear`; `lurkPoint` snaps to `freePointNear(p)` (nearest free reachable cell via `freeCellNear`), so targets are never inside walls or across water.
- **3D** (`buildMap3D`): the place is the built level's world (`levelInfo.world`, else `G.world`); `builtKey = mapKey()` = `levelInfo` `world:lv:attempt:fallback`, and `rebuild3D` rebuilds the map only when `mapKey()` changes. `cottage` → `makeCottage` (body, pitched roof along the long side, snow on winter roofs, door, windows); `water` → `makeWaterFor` (flat, no rim, so pieces join into one river; waves except winter) + `riverBanks` (one `InstancedMesh` of edge strips on water sides not next to water, a bridge or the map edge; stone edge in the schoolyard); fountain `pond` → `makeFountain` (bowl, water, column, bobbing drop in `waves`, `userData.baseY`); `maze` walls → boxes in `THEMES[place].maze` colours + `mazeDeco` (`InstancedMesh`: bumps, posts, snowballs, locker seams); `arena` walls via `walls.arena`. Maze walls keep `WALL_H` 0.85 (characters stay visible). `paintGround` draws `bridge` planks (across the crossing) and `square` cobbles. `tag(mesh, piece)` sets `userData.piece` for `__bb.mapPieces()`; `disposeTree` also disposes `InstancedMesh` buffers.

## Randomness (SPEC-008)
- **Gameplay** randomness goes only through **`rng()`** (`src/core/util.js`; a `mulberry32`, randomly seeded at start, so normal play is as before; SPEC-011: `window.__bbSeed`, set by a test's init script, seeds it at start instead, so the start-up `resetWorld` is seeded too). `rand(a, b)` draws from `rng()`. Users: item and star spawns (`spawnItem`, `spawnStar`), `randomFreePoint`, the Big One's look timers and `lookSign`, bot timers (`botWait`, lurk, `botAttackCd`), `makeLittle`, `resetWorld`, `steerPoint`'s default repath delay. **`seedRandom(n)`** reseeds it (`seedRandom()` without a number → random again). Same seed + same inputs → the same game.
- **Visual** randomness uses **`vrand(a = 0, b = 1)`** on `Math.random`: `burst` particles, the hearts during the hug ride, camera shake in `syncScene`, snow in `buildMap3D`, `randomOutfit`. It never touches `rng()`, so sim mode (no particles) draws the same `rng()` sequence as normal play. The level generator and the 3D decorations keep their own seeded `mulberry32`.
- **Guard**: `noGameRng(name, fn)` sets `rngOff = name` while `fn` runs. It wraps `generateLevel` (→ `layoutLevel`), `rebuild3D` and the render half of `frame()`. A `rng()` call inside it: with **`strictRng`** on (tests: `openGame` sets `window.__bbStrictRng` by an init script, the client passes it to `setStrictRng` at start) it throws `"<name>: gameplay rng() used; …"`; in normal play it falls back to `vrand()`, so the level still starts and the gameplay sequence is not consumed.
- `rngDraws` counts gameplay draws (a test checks that the autopilot's decision draws none).
- `tests/balance.spec.js` "same seed, same game" (`@fast`) also scans the game code (`src/**`): `Math.random` is allowed only in the `rngNext` seed and in `vrand`.

- **careful** (`autoGoalCareful`): a slipped Big One → straight at him; else a downed friend no bot is closer to (unless the Big One is dangerous and near him); else a bonus star or a non-banana item within reach while he can't see it; else his back (`backPoint`) — from far along a path around his view, near and in front of him circling sideways. `bigDangerous()` = no stun, slip, blush, `pushCd` or `noPush`. Kit: when it can use one and has waited `kitWait` s unhelped (or is already limping/resting). Kiss: facing him, in range, line of sight, he can be blushed.

## Tiptoe and hearing (SPEC-019)
- **Input → speed fraction**: the client's `deviceInput(l)` (SPEC-012: written into the player's input slot by `fillInputs` before each step) adds keys, gamepads and touch sticks into one vector; its length `t` (≤ 1) becomes the speed fraction `f`: `t < CFG.TIPTOE_MAX` → `TIPTOE_MULT × t / TIPTOE_MAX` (tiptoe, up to `TIPTOE_MULT`), else `t` (run). **`tiptoeKey(pi)`** caps `f` at `TIPTOE_MULT`: `TIPTOE_KEYS` = one player either Shift; two players P1 `ShiftLeft`, P2 `Slash` (the key left of Right Shift; "." on a Russian layout). Not Ctrl: with it P1's keys become browser shortcuts (Ctrl+W); Right Ctrl does nothing. `ShiftRight` stays P2's kit key (`kitKeyPlayer`). Keys alone give length 1 (run). The autopilot's `autoMove[pi]` is added after that, unchanged (its length already is the fraction). `updatePlayers` moves at `moveSpeed(l) × m` and stores **`l.speedFrac`** = `m` (0 when not moving); `updateBots` stores the fraction it steered with.
- **`isRunning(l)`** = state `ok`, `moving`, `speedFrac ≥ TIPTOE_MAX`. Tiptoe gives at most `TIPTOE_MULT`, which must stay below `TIPTOE_MAX` (`tests/invariants.spec.js` also checks `TIPTOE_MULT ≥ 0.5`).
- **Hearing in `updateBig`**: fields on `big` (set in `resetWorld`): `noise`, `hearCd` (s until he hears again), `hearFace` (the angle he turns to), `hearTurnT` (turn time left), `hearRate` (rad/s of that turn), `hearLook` (s he keeps looking). Every frame `hearCd` counts down and **`bigDeaf()`** (not `play`, `pendingWin`, `stun`, `blush`, `slip`, `pushCd`; not `noPush`) → `stopHearing()` (noise, turn and look to 0). **`bigListens()`** = `!bigDeaf()` — the one gate for `hearNoise`, the tap-tap lines and the careful autopilot's tiptoe. When he sees someone (`target`) the turn and look are dropped, the noise decays and the chase runs as before — `hearNoise` is not reached. Otherwise **`hearNoise(dt)`** runs before the search/look/patrol branches, so he still hears while he `search`es (a run decision: gating `search` too turned two balance targets red): while `hearCd ≤ 0` and `bigListens()` it sums `NOISE_RATE × dt × audible(l)` over all Little Ones. **`audible(l)`** = 0 unless `isRunning`, no cloak, not `inSafe`, within `HEAR_RADIUS × CELL` and at an angle ≥ `VISION_HALF` from `big.dir`; then 1 with `los` on the sight grid, else `HEAR_WALL`. Something heard → added; nothing heard (also during the cooldown) → `noise` decays by `NOISE_DECAY × dt`. At `NOISE_TURN` with a loudest runner (largest share, tie → nearest), SPEC-032 first rolls the chance: `CFG.HEAR_CHANCE` (`CFG.TUTORIAL.hearChance` 1 while `G.tutorialGame === 1`); a chance below 1 draws `rng()` (the gameplay stream, so sims repeat; a chance of 1 draws nothing — the pre-SPEC-032 game) and a miss sets `noise = 0`, `hearCd = HEAR_MISS_COOLDOWN`, logs `hearMiss { who, kind }` and returns (no turn). Heard: `noise = 0`, `hearCd = HEAR_COOLDOWN`, `hearFace`, `hearTurnT = HEAR_TURN_TIME`, `hearRate`, `hearLook = rand(HEAR_LOOK)` (a gameplay `rng()` draw), `state = "look"`, `timer ≥ turn + look`, goal and path cleared; event `heard { who, kind }`; a player with `!heardHintDone` starts the hint. In `look`: `hearTurnT > 0` → `turnToward(hearFace)`; then `hearLook` counts down without the look spin; then the usual spin.
- **Overhead mark**: **`bigMark()`** returns the one mark `drawMarkers` draws, in this order: `🍌💫` (slip), `?!` (stun), `💗` (blush), `❓` (`look` with `hearTurnT` or `hearLook` > 0), `👂` (`noise ≥ NOISE_WARN`), `💦` (`noPush`), `!` (chase), `""`. ❓ / 👂 are drawn at `fz(30 | 26, "main")`.
- **Heard hint**: `heardHintDone` (once per level for all players, the game's); SPEC-012: the game emits `hint { kind: "heard", slot }`, the client keeps the timer `ui.heardHintT` (`HEAR_HINT_TIME`) and `ui.heardHintPi`, counts it down each step (`stepGame`) and clears it with every new game. `heardHintOn()` = `play` and `heardHintT > 0`. `heardHintText()` = `heardHintTouch(tiptoeTap)` on a phone or a touch device (SPEC-032: `heardHintTouch` is a function of the tiptoe line), else `heardHint(heardKey())` (`heardKey2` for P2 with two players, else `heardKey1`). **`drawHeardHint(x, bottom, w, size, min, pad)`** draws a plate of up to two rows (`noteRows`, widths × `TEXT_TEST_SCALE`) with its bottom edge at `bottom`: desktop 600 px, centred above the rest bars and the kit hint (30 px higher on a touch screen in the first 5 s, above the touch hint); phone at the bottom left above the rest bars and the kit hint (and the touch hint in the first 5 s). `hudRects` id `heardHint` (the phone banner avoids it in `placePhoneBanner`); `heardHintRect` `{ x, y, w, h, text, rows, size }`, reset in `drawUI`.
- **Visuals**: `syncLittle` — tiptoeing (`moving`, 0 < `speedFrac` < `TIPTOE_MAX`): `rig` tilted by `TIPTOE_LOOK.lean`, lowered by `low`, bob `bob`, limb swing `swing` (`walk` grows with the fraction, so the steps are slower too). **`drawTapLines()`** (first in `drawMarkers`; nothing unless `bigListens()`): for every `audible` Little One `taps` white strokes with a dark edge on each side of the feet, `tap` UI px long (CSS px on a phone), shown while `|sin(walk)| > tapShow`; **`tapLines`** = their ids (also on the blink-off frames). `drawSticks` draws a dashed inner ring at `stickR() × TIPTOE_MAX`; **`stickMarks`** = `{ x, y, R, ring }` per stick drawn this frame (reset in `drawUI`).
- **Bots** (`updateBots`): `attack` within `(HEAR_RADIUS + TIPTOE_NEAR) × CELL` of him → speed × `TIPTOE_MULT`; `lurk` → × `TIPTOE_MULT` within `HEAR_RADIUS × CELL`, else × `CFG.BOT_LURK_MULT` (0.8, the old lurk speed; below `TIPTOE_MAX` 0.85, so silent too); `rescue`, `flee`, `leave` → full speed (running).
- **Autopilot**: `autoTiptoe(l)` = `bigListens()`, within `(HEAR_RADIUS + TIPTOE_NEAR) × CELL`, at an angle ≥ `VISION_HALF` from `big.dir`; then `careful` caps the `autoMove` length at `TIPTOE_MULT`. `reckless` always runs.

## Coins economy (SPEC-009)
- **Ledger**: **`addCoins(reason, amount)`** and **`spendCoins(item, amount)`** (`src/core/economy.js`) are the only code that changes `progress.coins`. `addCoins` clamps the amount so the coins never go below 0, skips 0, adds, `logCoins(reason, amount)`, saves, returns what it added. `spendCoins` returns `false` and changes nothing when the coins are short; else subtracts, logs `buy:<item>` with the negative amount, saves, returns `true`. `logCoins` pushes the `coins` event into `events` (via `logEvent`) and a copy into **`ledger`** — the session list since page load (not cleared by `startGame`, capped at `CFG.EVENT_LOG_MAX`; `__bb.ledger()` returns copies). Reasons: see the event log.
- **Source scan**: `tests/economy.spec.js` "only the ledger writes coins" (`@fast`, Node, `coinWrites(src)`) fails on any write to a `coins` member outside the bodies of `addCoins`/`spendCoins` — `=`, compound `op=`, `++`/`--`, `["coins"]`, aliases, destructuring targets, `Object.assign(…, { coins })`, `Reflect.set`/`Reflect.defineProperty`/`Object.defineProperty`, and `progress = …` other than `freshProgress()` / `loadProgress(…)` or a `...progress` spread; it plants one write of each kind to prove the scan finds it. ## Errors and lifecycle (SPEC-025 phase 1)
- **Early errors** (`index.html` non-module script, before any module runs): `window.__bbBoot = { lang, failed, early, onError, tryAgain, fail(kind) }`. Its `error` (capture) and `unhandledrejection` handlers queue errors in `early` until `errors.js` `initErrors` logs them and sets `onError` (→ `reportError`). A rejection whose reason has `benign: true` (a refused optional browser feature) is no error (AC 7c); the game's own promises (`actx.resume()`, fullscreen, …) all have a catch, and the fullscreen act runs on `pointerup`. A failed `<script>` load before `__bbReady` → `fail("needsInternet")` only when `navigator.onLine === false`, else `fail("startFailed")`.
- **Start failures** (AC 7b): `fail(kind)` replaces the progress bar of `#loading` with `#start-failed` — `noWebGL` (no `getContext("webgl2")`, probed in the script and again in `boot()`, or the renderer cannot be created), `startFailed` (+ the `#try-again` button = `location.reload()`, text `tryAgain`), `needsInternet`. The texts are inline in en/es/pt/ru (language: the save, then `bebebe-lang`, then the browser). A slow start keeps the progress bar (no timer message). Never after `__bbReady`, never on `file://` (its own notice).
- **Oops card** (AC 7): `reportError(err)` → `logError` and, once `__bbReady`, the DOM card `#oops` once (the game pauses if it was playing). Buttons: in a level `resume` (Continue; resumes only if the card paused) and `restartLevel` (`retryLevel`, or the practice game again); elsewhere `resume` and `home`; the same error again right after Continue also gets `tryAgain` (reload). While a card is open, keys and pad buttons go to it (`cardOpen`, `pressCard`), not to the game: Left/Right move between its buttons, Enter or pad A presses one.
- **Error log** `bebebe-errors` (local only, never sent): the last `CFG.ERROR_LOG_MAX` entries `{ message, stack, version, mode, level, count }` — message cut at `CFG.ERROR_MESSAGE_MAX`, the first `CFG.ERROR_STACK_LINES` stack lines, `version` = `SRC_HASH` (`<meta name="src-hash">`) until a game version exists; a non-Error reason is logged only by its type (never its content: no names, no save data). The same error repeating counts up in its entry (written at most every `CFG.ERROR_LOG_WRITE_EVERY` s, and on hide and before a reload). Its viewer (grown-ups page) is phase 2.

Import maps also remap the modules' relative imports, so a shell only ever loads its own module versions (no mix of old and new; no dynamic `import()` in the game). Rerun after any change to `src/` and after merging `master` into a branch; `--check` only compares; `tests/pwa.spec.js` fails on stale hashes, import map or `SRC_HASH`. It also writes the `./vendor/three/…?v=<hash>` import map entries and `THREE_VERSION` (`r` + the vendored `REVISION`) + `PRECACHE_THREE` into `sw.js`. A module change changes no `SW_VERSION`.
- **Version and `SW_VERSION` (SPEC-025 AC 12)**: the game version is `package.json` `version` (semver; `1.0.0-dev` between releases). `npm run precache` writes it into **`src/version.js`** (`VERSION`; the grown-ups page and the error log show `buildVersion()` = `<VERSION>+<SRC_HASH>`) and writes `SW_BUILD`, `SW_STRATEGY` and `SW_VERSION` = `bebebe-<version>-b<SW_BUILD>` into the generated block of `sw.js`. `SW_STRATEGY` is a hash of `sw.js` outside its generated blocks plus the cached shell files (icons, manifest); when it changes, precache adds 1 to `SW_BUILD`. Nobody edits these by hand; `--check` and `tests/tooling.spec.js` fail on a stale value. A release (`npm run release -- X.Y.Z`, `docs/release.md`) changes the version, so it renames the src and assets caches: installed apps fetch code and sprites once more (three.js keeps its own cache).
- **Install**: first fetches `./` and `./index.html` (`cache: "reload"`) and refuses to install unless both carry this `SRC_HASH` (a half-deployed site leaves the active version alone); a complete src cache of the same `SRC_HASH` (a sprite-only or three.js deploy) is kept and only gets the fresh shell; else the src files are added all or nothing (a failed install deletes only a cache it made), then the shell and the marker; then three.js and the sprites; `skipWaiting()`.

- **Fetch**: navigations and `index.html` **network-first** exactly as before (the cache answers when the network fails, returns a non-OK status, or takes longer than `NET_TIMEOUT_MS`; root fallback `./`; the cached shell is looked up in this worker's src cache first). **Shell rule**: a network-fetched `index.html` is stored only into the complete src cache named by its own `<meta name="src-hash">`; if there is none yet (the new worker has not finished installing) it is shown but not cached, so a cached shell always has its modules. Versioned modules (`/src/…?v=`) cache-first from any of our caches, else the network, never written; an unversioned `/src/` URL (the shell never asks for one) network only — no cached copy of another version (SPEC-011 Phase C); `/vendor/` cache-first from the three.js cache (`CACHE_THREE`), else the network, never written; `/assets/` cache-first (`CACHE_ASSETS`); `/icons/` cache-first; everything else (the manifest, `v1-2d/`, an unversioned file) network-first with our caches as fallback, nothing written — `v1-2d/` is no longer cached at runtime.
- **`vendor/three/`** (SPEC-025 AC 1/1b/2): the minified r187 build files under the original names (`three.module.js` imports `./three.core.js`; the npm package ships no minified build, so they are jsDelivr's Terser minification of the npm files, licence headers kept) + `LICENSE` + `package.json`; listed in `THIRD_PARTY_LICENSES.md`. `npm run vendor:three` (`scripts/vendor-three.js`, a dev tool) re-creates them from the version pinned in `package.json` (must equal `node_modules/three`), then runs precache. ## Save data (SPEC-025 phase 2: `bebebe-save`)
- **Backend** (`storage.js`, AC 3b): `{ get, set, remove, keys, sync }`, every method a Promise that never rejects — `get` → the text, `null` (absent) or `undefined` (could not be read); `set` / `remove` → true when it worked; `keys` → the stored `bebebe-*` keys. The default `localBackend` is `sync` (each write done inside the call, so a flush on hide completes before the page can be killed); every error caught. The tests swap in an async in-memory store through `window.__bbSaveBackend` (read by `loadSave`, wrapped by `wrapBackend`). A native backend (store app) is a later spec.
- **One key** `bebebe-save`, owned by `save.js`: `{ version, progress, outfits, names, lang, migrated, persist, langAsked, … }`. `version` = `SAVE_VERSION` (1; a schema id in `save.js`, not a `CFG` number). `progress` = the shape below (`seen` inside it); `outfits` by item id `{ p1: { hair, hat, jacket, pants }, p2: {…}, big }` (AC 3c: `outfitsToIds` / `outfitsFromIds` in `outfits.js`; an unknown id → that slot's default, so a list may change its order); `names` = the typed names (below); `lang` = `en|es|pt|ru`; `migrated` = old key → FNV-1a fingerprint (hex) of its raw value at the last migration (`null` = absent); `persist` = `{ asked, granted }` (AC 5); `langAsked` (SPEC-032, an added field) = `false` on the first save of a device with nothing stored (the language screen is due, `langPending()`), `true` after a choice or Escape (`answerLang()` queues the save at once); older saves have no field and never see the screen; a restore / undo / import keeps this device's value.
- **Schema rule** (AC 3, CLAUDE.md hard rule 7): fields are only ever added; a change of a field's shape gets a new field name. What this version does not know is kept and written back (`holdSave` / `holdProgress` → `held`, merged in `saveObject`): top-level fields, worlds, world fields, owned lists and ids, upgrade keys, seen keys, outfit ids (while that slot stays on its default). A save with a higher `version` (`future`) is played and written back with its own `version` and every field it had, never downgraded: a known field that fails this version's check (`TOP_VALID`, `badProgressFields`) is written back unchanged (the default only in memory), and levels past this build's last one stay. Known fields are validated and defaulted (AC 3d, `loadProgress`).
- **Migration** (AC 3, `loadSave` with no `bebebe-save`), in order: (1) read every old key raw (`OLD_KEYS` = `bebebe-progress`, `bebebe-outfits`, `bebebe-names`, `bebebe-lang`); (2) the key-presence facts first — no `bebebe-progress` = a first launch (SPEC-032: nothing stored at all → English and `langAsked: false`, no browser detection; otherwise `detectLang` as in SPEC-028), a progress without `owned` gets the worn paid clothes (`adoptWorn`; only on a real migration, never after a failed load), a flat save moves into the Park, outfits `v` < 2 with `big: 0` → the dad; (3) build `bebebe-save`, write it, read it back; (4) the fingerprints are stored in `migrated` with it, so the record exists only if the write was intact. **Old keys are never written or deleted** (only by "Erase all data"); `bebebe-place` and `bebebe-skins` (v1-2d) are not read.
- **Stale-tab merge** (`mergeStale`, every start): an old key whose fingerprint differs from `migrated` (an old tab or an old cached build wrote it) is merged again after a `-before-migration` snapshot: best stars per level, the higher `unlocked`, `won`, owned items and seen scenes joined; coins, stock and upgrades stay `bebebe-save`'s; a changed old outfits / names / lang key is ignored (`bebebe-save` wins). Then the new fingerprints are stored. A reset keeps `migrated`, so the old keys are not migrated again.
- **Copies** (each stored as `{ at, save }`): `bebebe-save-backup` (the previous save, written when a write changes it); `bebebe-save-session` (the save as loaded at the first start of a local day — replaced only when the stored copy is `CFG.SAVE_SESSION_DAYS` or more days old, so a bug later that day never reaches it); snapshots `bebebe-save-before-migration`, two reset copies `-before-reset` and `-before-reset-2` (the save of a reset is always kept; of the older reset copies the one that holds more stays with it — fewer stars, then fewer owned items, then fewer coins = holds less, `holdsLess` — so a second reset after a little play loses neither progress; of the pair the one that holds more is `-before-reset`, the undo; both are listed under Restore a copy), `-before-import`, `-before-restore` (one slot: each restore replaces it); `bebebe-save-broken` (a stored save that fails to parse or validate, kept as raw text before anything is written; never overwritten while one is there; cleared by a restore or an import). `COPY_NAMES` = the recovery order: backup → session → snapshots newest first.
- **Recovery** (AC 4): a broken `bebebe-save` loads the newest valid copy (note `saveRecovered`), else the old keys as frozen at the migration (`saveRecovered`, no gifts), else a fresh game (`freshStart`). The grown-ups page lists the valid copies (`listCopies`) and restores one (`restoreCopy`: the save before it becomes `-before-restore`; restoring `reset` = undo, that copy is then removed).
- **Writes** (AC 3b): `queueSave()` puts the whole save into `pending` (only the last write per key waits) and flushes on a microtask (several changes of one task = one write); `flushSaves()` also runs on hide / `pagehide` (`lifecycle.js`) and before a WebGL reload. Writes are applied in call order: a `sync` backend writes inside the call, any other is chained after the previous write answered (`lastWrite`). Nothing is queued before `loadSave` applied the stored save (`loading`, `loaded`) or after "Erase all data" (`erased`).
- **Failed storage** (AC 4b): the probe at start (`bebebe-probe`: write, read back, remove) or any failed `set` → `saveInfo.noSave`: the game plays from memory and the menus show `noSave` once per session (no error card). A failed probe or an unreadable `bebebe-save` also sets `saveInfo.saveOff`: the stored keys are still read and played, but this session writes no `bebebe-save*` key (a nearly full storage could otherwise take a fresh save over the real one).
- **`persist()`** (AC 5): `navigator.storage.persist()` asked once, after a start that can write, only where it never prompts — skipped on a Firefox / Gecko user agent (`promptsForPersist`); `persisted()` already true → recorded as granted without asking. The answer is `persist`.
- **Save states** (`saveState()` = `__bb.save.info`): `loading` (inside `loadSave`) → `loaded`; `erased` (after "Erase all data": nothing more is written, the page reloads); `future` (the save is from a newer version); `noSave` / `saveOff` (above); `recovered` (`backup` | `session` | a snapshot name | `old` | `fresh` | null); `notes` (due) / `shown`; `copies` (stored); `pending` (writes waiting); `persist`.
- **The parents' code** (AC 6c): `BB1.<base64url of the UTF-8 JSON save>.<FNV-1a hex of that JSON>` (no `CompressionStream`); the JSON carries `version` and leaves out this device's `migrated`, `persist` and `langAsked`. `readCode` ignores spaces and line breaks; a wrong prefix, part count, base64, checksum or root → `codeBad`, a higher `version` → `codeTooNew`. `importSave` takes the `-before-import` snapshot, then the code's save goes through the normal schema (`replaceWith`: this device's migration record and persist answer stay, so its old keys are not merged in). Import accepts codes of every save version: the code is the way to move progress from the web / PWA to a store app (another origin).
- **Erase all** (AC 6b, `eraseAll`): waits for the writes already started, then removes every `bebebe-*` key (the backend's `keys()` + `SAVE_KEYS` + `OLD_KEYS` + `bebebe-place`, `bebebe-skins`) — the one place old keys are deleted; then the page reloads as on a new device (first-launch flow).
- The inline (non-module) script of `index.html` reads the language from `bebebe-save`'s `lang`, then `bebebe-lang`, then the browser.
- **`progress`** (old key `bebebe-progress`; SPEC-006, SPEC-009, SPEC-016, SPEC-022 `seen`; SPEC-029 `seen.tutorial`, the same `cleanSeen` over `SEEN_IDS` = `SCENE_IDS` + `tutorial`, fixture `pre-spec-029.json`): SPEC-022 adds `seen: { intro, boss_park, boss_field, boss_city, boss_school, bonus_beach, bonus_winter, ending }` (`cleanSeen`: only `true` counts, unknown keys dropped, missing or broken → all `false`; fixture `pre-spec-022.json`). SPEC-026 changed no shape: `pre-spec-026.json` (bought at the old prices) loads its kits, upgrade levels and clothes unchanged — nothing refunded or re-charged. `{ worlds: { park|field|city|school|beach|winter: { unlocked: 1..20, stars: { [n]: 1..3 }, won: { [n]: true } } }, lastWorld, coins, inv: {mittens, mega, kisses, rescues}, equip: [p1, p2], owned: { hats: [id], jackets: [id], pants: [id], big: [id] }, upgrades: { fastFeet, longItems, quickHelp } }`.
