# CLAUDE.md — bebebe-game (BeBeBe Atrapar)

A top-down 3D arcade game that Andrei makes with his kids from their scenario and drawings: the team of **Little Ones** (1–2 players + bots) against the **Big One**. Hug him from behind to take his hearts; if he sees you, he pushes you and your leg breaks; friends rescue you. The kids are the product owners: their decisions are the rules.

- **Game rules (source of truth):** `docs/game-design.md` — every rule says whose decision it is ("решение детей" / "придумал Claude"). A kids' rule never changes without a spec that says so.
- **Code map:** `docs/architecture.md` (the module table of `src/`, character states, the `window.__bb` debug object).
- **How work is run:** `docs/process/orchestration-rules.md` + `docs/process/run-templates/RUN_S|M|L.md`.

## What is in the repo

- `index.html` + `src/` — **v2, 3D**: the shell and ES modules, no build step (SPEC-011): `src/core/` is the game itself (rules, level generator, bots, the Big One; runs in Node too), `src/i18n.js` and `src/story.js` are shared data, `src/client/` everything a player sees, hears and touches (3D in `three/`, 2D screens in `ui/`, input, sound, saves; `main.js` is the entry and the one place that starts the game, `debug.js` builds `window.__bb`). `index.html` is only the shell: markup, CSS, a small non-module script (offline hint, `file://` notice), the import map and `<script type="module" src="./src/client/main.js?v=<hash>">` — no game code (a test checks it). Module table: `docs/architecture.md` "Modules". Three.js **r187** is imported as the bare name `"three"`, resolved by one `<script type="importmap">` to the vendored minified build in `vendor/three/` (SPEC-025 AC 1; licence in `THIRD_PARTY_LICENSES.md`): no file is loaded from another host, the game runs offline from the first launch.
- PWA files: `manifest.webmanifest`, `sw.js` (offline cache), `icons/` (PNGs + the `icon.svg` favicon, all made from `art/2_icon.webp` by `npm run icons` with `sharp`). Published on GitHub Pages: **https://andrei-danilin.github.io/bebebe-game/** by `.github/workflows/pages.yml` on every push to `master`: the sharded tests and, in parallel, a `build` job (`npm run site -- --stamp <sha>` → `_site/` + `version.txt`), then `deploy` (two `deploy-pages` attempts, then a check that the live `version.txt` is this commit; SPEC-011). CI (SPEC-023): `.github/workflows/tests.yml` runs the whole suite in 4 shards plus a `lint` job (`npm run lint`) on every push of a `SPEC-*` branch (and is reused by `pages.yml`); `.github/workflows/balance.yml` makes the balance report on demand.
- Art (SPEC-020): `art/` — Andrei's source pictures (never written by code, not deployed); `scripts/assets.js` + the manifest `scripts/assets.json` turn them into `assets/*.webp` (committed, deployed, drawn by the 2D layer; every sprite has a code-drawn fallback). See `docs/architecture.md` "Art".
- `v1-2d/index.html` — v1, 2D canvas, offline. Frozen: no new features unless a spec names it.
- `tests/core/` — Node tests of the headless core (SPEC-012: `npm run test:core`).
- `tests/` — Playwright tests; every test opens the game over http from `scripts/serve.js` (SPEC-011; `pwa` = service worker and manifest; `modules` = the `__bb` surface, the import map, the lint config, the module rules (core never depends on the client, hooks, Node import, the module table of `architecture.md`, same-game and save references); `site` = the built `_site/` plays; `env` = GPU/priority of the test machine); three.js is vendored, so the tests run offline and load exactly the files players get (`offline` = the request audit and the shipped-files URL scan, SPEC-025). `tests/test-env.js` (GL backend, priority), `tests/global-setup.js`, `tests/pw.js` (failure screenshots).
- Tooling (SPEC-011): `scripts/site.js` (the one list of site files; `npm run site` → `_site/`, what Pages publishes), `scripts/lint.js` + `eslint.config.js` + `scripts/eslint-imports.js` (`npm run lint`: ESLint over `src/` and `scripts/`), `scripts/precache.js` (`npm run precache`: module hashes). Dev-only, not part of the site.
- `docs/` — `game-design.md` (rules), `architecture.md` (code map), `process/` (orchestration rules, run templates).
- `specs/` — `SPEC-NNN-*.md` (one feature each), `BACKLOG.md`, `_archive/` (done specs).
- `claude-setup/` — the committed source of the Claude Code agents and skills; `npm run claude:sync` copies them into `.claude/` (local, gitignored), where Claude Code finds them. Edit `claude-setup/`, never `.claude/` directly.

## Hard rules

1. **No build.** The site is `index.html` + `src/` (ES modules) + PWA files; it opens over http only (`npm run serve`, Pages, the installed app). No bundler, no framework, no new runtime dependency without a spec. `src/core/` never depends on `src/client/` or three.js.
2. **Four languages for every string.** Every text a player sees goes into `I18N` for `en` (default), `es` (Argentina, voseo: "agarrá", "tenés", "campera"), `pt` (Brazil, pt-BR, *você*: "pegue", "você tem", "jaqueta"; SPEC-028) and `ru`; every name object (clothes, looks) has all four (`Nm(en, es, pt, ru)`). `tests/i18n.spec.js` fails on a missing key or name.
3. **Numbers live in `CFG`** — the rules, generator and balance in `src/core/config.js`, the look/UI numbers in `LOOK` of `src/client/look.js` (same key names; `__bb.CFG` shows both) — and `GLOVES`, `THEMES`, the outfit lists: no magic numbers in logic. A spec that changes a rule changes the `CFG` value and the line in `game-design.md`.
4. **JS style:** ES2022, `let`/`const` only (never `var`), short comments in Russian or English, code identifiers in English.
5. **Kid-friendly:** nothing scary or violent in visuals or texts (the Big One "pushes", nobody "dies"); big readable UI; works with touch, keyboard and gamepad.
6. **Keep `window.__bb` working.** Tests drive the game through it; a spec that adds state the tests need exposes it there.
7. **Progress is player data.** One save key, `bebebe-save` (`{ version, progress, outfits, names, lang, … }`), and its copies (`bebebe-save-backup`, `-session`, `-broken`, `-before-migration`, `-before-reset`, `-before-reset-2`, `-before-import`, `-before-restore`), all written only by `src/client/save.js` through `src/client/storage.js` (the only code that touches `localStorage`; SPEC-025). The old keys `bebebe-progress`, `bebebe-outfits`, `bebebe-names`, `bebebe-lang` are read once at the migration (and checked by fingerprint for stale-tab writes), never written or deleted — except by "Erase all data on this device" on the grown-ups page; `bebebe-place` is never read. **Fields are only ever added; a change of a field's shape gets a new field name.** Unknown fields and a newer version's save are written back unchanged; loading never throws (broken → a copy, else fresh). `bebebe-errors` (the local error log; never sent, never holds names or saves) stays its own key. See `docs/architecture.md` "Save data".
8. **`sw.js` `SW_VERSION` is derived, never bumped by hand** (SPEC-025 AC 12): `npm run precache` writes it as `bebebe-<package.json version>-b<SW_BUILD>`, and the build counter `SW_BUILD` goes up by itself when the cache strategy (`sw.js` outside its generated blocks) or a cached shell file (an icon, the manifest) changed — so after such a change, as after any change to `src/`, rerun `npm run precache` (a test fails on a stale block); it also writes `src/version.js` (`VERSION` = `package.json` `version`, semver, shown on the grown-ups page). A change to `index.html` alone changes nothing: it is network-first. **A change to `src/` needs no bump either: rerun `npm run precache`** (also after merging `master` into a branch) — it writes each module's content hash into the import map of `index.html` (`./src/…/x.js?v=<hash>`) and into the entry script's `src` (`main.js?v=<hash>`: an entry `src` is not remapped by the import map), `SRC_HASH` into `<meta name="src-hash">` and the module list + `SRC_HASH` into `sw.js`; the shell + modules cache is named `SW_VERSION-src-SRC_HASH`, so installed apps fetch the new modules; a test fails when the committed hashes do not match the files (SPEC-011 AC 9). A new three.js version is a spec of its own: new files in `vendor/three/` (the import map's `"three"` → `./vendor/three/three.module.js`), `THIRD_PARTY_LICENSES.md`, `three` in `package.json`, then `npm run precache` (it writes the vendor URLs' hashes into the import map and `THREE_VERSION` + `PRECACHE_THREE` into `sw.js`; a test checks the vendored REVISION = `package.json` = `node_modules`). A redrawn icon → `npm run icons`, then `npm run precache` (the next `SW_BUILD`). Sprites in `assets/` need no bump: `npm run assets` writes their list and `ASSETS_HASH` into `sw.js`, and the sprite cache is named `SW_VERSION-assets-ASSETS_HASH`, so installed apps fetch redrawn sprites (three.js has its own cache, `bebebe-three-<THREE_VERSION>`, so a code deploy never downloads it again).

## Workflow (spec-driven) and Git

**Roles.** Specs are written by Claude in the claude.ai project "BeBeBe Atrapar" (with Andrei and the kids) and committed to `master` as `specs/SPEC-NNN-short-name.md` before a run (that Claude cannot write into `.claude/` on this machine, which is why specs and docs live outside it). **Claude Code implements, commits and merges** — unlike ce-fsa-app, no user step is needed for commits or merges. Andrei starts a run by pasting the matching template from `docs/process/run-templates/` into `claude` at the repo root.

1. One feature = one spec (format: `specs/README.md`). Work strictly within one spec; anything new that comes up goes to `specs/BACKLOG.md`, not into the running spec.
2. **Branch** `SPEC-NNN-short-description` off `master` (`git branch --show-current` first; never edit on `master`).
3. **TDD**: for each acceptance criterion write the failing Playwright test first, then the code.
4. **Verify** (agent `tester`; speed rules, Andrei 2026-11-23): **no local whole suite.** Locally only `npm run test:fast` + the test files of what changed (`npx playwright test tests/<file>` or `-g "<name>"`); phone layouts locally at **667×375 only** (`-g "667"`; CI runs every size). **The whole suite runs on CI:** push the spec branch (`git push -u origin SPEC-NNN-...`, never `--force`), find the run of exactly that commit (`gh run list --workflow tests.yml --commit $(git rev-parse HEAD) --limit 1`, retried every ~10 s until it appears), then `gh run watch <id> --exit-status` the **Tests** workflow (`tests.yml`, 4 shards + `lint`); red → investigate from its artifacts (`gh run download <id>`: the merged HTML report, error context + failure screenshots), fix, push again. **The merge happens only when that run is green.** **Balance:** a spec that changes gameplay numbers or rules gets its report from GitHub: `gh workflow run balance.yml -f ref=<branch>`, `gh run list --workflow balance.yml --limit 5` → the run titled `Balance <branch>` created after the dispatch, `gh run watch <id> --exit-status`, `gh run download <id> -n balance -D reports`, commit the updated `reports/balance.md` + `reports/balance.json` on the branch, and list the red targets in its final report (red is not a stop by itself unless the spec's ACs say so); a changed number also needs `npm run docs:numbers`.
5. **Review**: **one pass** on `git diff master...<branch>` and the spec only — tiers M and L: `code-reviewer` + `architect-reviewer` **in parallel**; tier S: `code-reviewer` only. CRITICAL/HIGH are fixed in **one** fix round, then **one** check of the fix commits (`code-reviewer` on those commits only). No second full review.
6. **Commit** in small steps, explicit paths only, message `SPEC-NNN: <what>`, ending with the attribution lines from your system reminder. Use the machine's git identity; never change git config.
7. **Close on the branch, before the merge** (so close and merge go out in one push): agent `doc-keeper` updates `game-design.md`, `architecture.md`, `README.md` if the spec changed a rule, a structure or a command (commit `SPEC-NNN: docs`), plus one plain-words line for the spec under `## [Unreleased]` in `CHANGELOG.md` (releases: `docs/release.md`); the spec's `Status:` line becomes `done (merged by "Merge SPEC-NNN", see git log)` (the merge hash does not exist yet), the file moves to `specs/_archive/`, the run-state file `specs/SPEC-NNN_RUN_STATE.md` is deleted; commit `SPEC-NNN: close`; before this push, bring `master` in if it moved on — `git fetch origin && (git merge-base --is-ancestor origin/master HEAD || git merge origin/master)` (never rebase), so the merge result itself is tested; push the branch once — its Tests run (found by commit) must be green.
8. **Merge, push, deploy**: `git checkout master && git merge --ff-only origin/master && git merge --no-ff SPEC-NNN-...` (message `Merge SPEC-NNN: <title>`), then `git branch -d SPEC-NNN-...`; no local suite on `master` (CI tested the branch; the Pages workflow tests `master` again before the deploy). Remote `origin` = `github.com/Andrei-Danilin/bebebe-game`: `git push origin master` (never `--force`), then `git push origin --delete SPEC-NNN-...` (the remote spec branch), then find the Pages run of that commit (`id=$(gh run list --workflow pages.yml --commit $(git rev-parse HEAD) --limit 1 --json databaseId --jq '.[0].databaseId')`, retry until it appears) and `gh run watch $id --exit-status` until it (sharded tests + deploy) is green (a cancelled run = superseded by a newer push: watch the run of the last commit). A red deploy is reported, not retried blindly; the `deploy` job already tries `deploy-pages` twice and then checks that the live site serves the commit (SPEC-011). A red deploy **with green tests** ("Fetching artifact metadata failed" and the like) is recovered once with `gh run rerun <id> --failed` only when that run's `build` job was green and its commit is still the HEAD of `origin/master` (it reruns only `deploy`, which deploys the artifact `build` uploaded once); otherwise a fresh `gh workflow run pages.yml --ref master`. **Queues:** the next spec may start while the previous deploy is still running; its tests must be green before the next spec's own merge; a deploy-only failure with green tests does not block the next spec (Andrei). Final report: short table AC → test, test counts, CI run ids, review findings, open points.

Never: `git push --force`, pushing anything but `master` and your own spec branches (`SPEC-*`; never other people's branches), `git reset --hard`, `git branch -D`, rewriting history on `master`, editing `v1-2d/` or `node_modules/`.

**When a deploy breaks the game for the kids** (Andrei, D-7, 2026-11-26): a **revert of the merge commit** (`git revert -m 1 <merge sha>`, message `revert: <what>`) may be pushed **straight to `master`** — the Pages workflow still tests it before it deploys; and a known-good tag is redeployed with `gh workflow run pages.yml --ref master -f ref=vX.Y.Z` (the `ref` input of `pages.yml`, default `master`; tests, build and the live check use that commit; `docs/release.md` "Rollback"). Nothing else goes to `master` without a spec branch. Afterwards the fix is a normal spec. Spec branches get no pull requests (the Tests workflow runs on their pushes; a PR into `master` would run everything a second time — `pull_request` is for Dependabot).

**Dependabot** (SPEC-025 AC 11; `.github/dependabot.yml`): weekly grouped PRs for the npm dev dependencies and the GitHub Actions (pinned by commit SHA); `three` is ignored (a new three.js is a spec, hard rule 8). Such a PR is tested by the Tests workflow on the PR (`pull_request` into `master`); review it: read the changelogs of what moved (a major → check the breaking changes, e.g. a new ESLint rule set or Playwright API), then **CI green on the PR** (`gh pr checks <n> --watch`) → merge it into `master` locally as a `deps:` commit: `git fetch origin && git checkout master && git merge --ff-only origin/master && git merge --no-ff origin/<bot branch> -m "deps: <what>"`, run `npm ci` + `npm run lint` + `npm run typecheck` + `npm run test:core` locally, `git push origin master` (the Pages run tests and deploys as usual), then GitHub closes the PR and deletes the bot branch. Nobody pushes to the bot's branch (a needed fix → a spec). A red PR is left open with a comment, not forced.

**`master` ruleset** (SPEC-025 AC 11b; RR-84): `.github/rulesets/master.json` blocks force-pushes and the deletion of `master`; it has no required checks, so the direct merge flow above still works. Beside it, `.github/rulesets/tags.json` keeps the release tags `v*` (docs/release.md) from being deleted or moved. Andrei applies both once (`gh api -X POST repos/Andrei-Danilin/bebebe-game/rulesets --input .github/rulesets/master.json`, the same with `tags.json`); a change to a file is applied the same way with `-X PUT …/rulesets/<id>`. Runs never apply or change them. Who else can act on the repo (a backup person, account access) is decision D-6.

## Test gotchas

- **Text that fits only with your fonts is a CI red** (it happened twice in SPEC-033): before a push run the changed text/layout tests also as `PW_FONT=ci npx playwright test tests/<file> -g "…"` (the phone and fit tests: `-g "667"`), and keep a margin (`LOOK.TEXT_TEST_SCALE`-style ×1.15 / ×1.3 in the test; `PHONE_PRICE_FIT` and `card.btnGrow` in the code). CI keeps `retries: 0` (D-15): a flaky test is fixed at the root, not retried.
- Locally the tests draw on the GPU, on CI with software WebGL (SwiftShader, slow per frame; `PW_GPU=0` locally does the same): gameplay is advanced with `step(page, seconds)` (logic only), not by waiting. A test that checks only logic or numbers opens the game in sim mode (`openGame(page, { sim: true })`, or the `simPage` fixture of the shared-page specs); in sim, `frames()`, `page.screenshot()` and the drawn state of `__bb` (`__bb.SIM_DRAWN`) throw — a test that checks drawing uses a rendered `page` (`docs/architecture.md` "Tests and CI").
- Specs require `./pw` (= `@playwright/test` + failure screenshots of every open page), not `@playwright/test` directly.
- Core tests (SPEC-012) are `tests/core/*.test.mjs` run by `node --test`, never by Playwright (`playwright.config.js` `testMatch: "**/*.spec.js"`); they import `src/core/index.js` directly, make games with `createGame({ …, fx: false })` (or drain `g.fx`) and step them at `CFG.STEP` (1/60 s). In a page, `__bb` reads the active game (`__bb.game`): the local game in play, the menus' showcase otherwise; a 💋 / 🩹 press through a key, a button or `__bb.game.inputs.p1.kiss / .kit` fires at the next step (`__bb.update`), while `__bb.throwKiss` / `useRescueKit` / `giveReward` are shims that act at once (`docs/architecture.md` "window.__bb").
- Tests that change `__bb.CFG` restore it and call `__bb.clearLevelCache()` (the level cache keeps the accepted attempt per level).
- `openGame()` clears `localStorage` once per test; a test about saving reloads the page with `reloadGame(page)` (reload + wait for ready + seed again) and checks `window.__bb.progress` or the stored save with `storedSave(page)` (flushes the write queue, returns the parsed `bebebe-save`). Tests never read the old keys to check a save (nothing writes them since SPEC-025); a test that needs an old save on the device uses `putOldSave(page, keys)` (removes every `bebebe-save*` key, writes the old keys) and then `reloadGame`, which migrates them. Writes are queued (a microtask): `__bb.save.flush()` before reading `localStorage` directly.
- Over http (SPEC-011): every test opens the game at `http://localhost:8123/index.html` (`PORT`); Playwright starts `scripts/serve.js` as its `webServer`, or reuses a running one only if it serves this checkout (header `X-Bebebe-Root`, checked in `tests/global-setup.js`; another checkout's `npm run serve` fails the run — stop it or set `PORT`). Service workers are blocked (`serviceWorkers: "block"` in `playwright.config.js`) except in `pwa.spec.js` (`openGameHttp()`).
- Seeds (SPEC-011): every test game is seeded from the test (FNV-1a of file name + title path, `testSeed()` in `helpers.js`): `openGame`/`openGameHttp` set `window.__bbSeed` so the boot is seeded too, then seed again; `resetGame`/`reloadGame` reseed. A failed test prints `[seed] … rng seed N`; a game is reproducible from it in sim only (a rendered page draws `rng()` in its frames). A smoke scan fails on a `startGame(`/`resetWorld(` with no seeded `seedRandom(n)` before it (or after a reload). Claims about a spread of outcomes run over several seeds with a bound.
